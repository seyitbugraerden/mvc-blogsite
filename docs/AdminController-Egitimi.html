DERS 02 · BÖLÜM 01

Okumadan yazmaya geçiyoruz

SiteController içeriği gösterir; AdminController onu yönetir.

Önceki derste bir URL’nin veritabanı sorgusuna ve view’a nasıl bağlandığını gördük. Bu derste ters yönü de izleyeceğiz: kullanıcı inputa bir değer yazar, form gönderilir, C# nesnesi oluşur, doğrulanır ve veritabanına kaydedilir.

GET /admin/posts/ilk-yazim/edit
  → AdminController.Editor → ContentPage → Edit.cshtml
  → Kullanıcı formu değiştirir
POST /admin/posts/ilk-yazim/edit
  → SavePost → Save → doğrulama → SaveChangesAsync
  → Redirect → Edit.cshtml yeniden açılır
GET /blog/ilk-yazim
  → SiteController → güncel kayıt → ziyaretçi view’ı

Rehber, projenin 4c8cf8c sürümündeki davranışını anlatır. Uygulama kodu bu ders için değiştirilmez. Kısaltılmış kodlar öğretici örneklerdir; sonda controller’ın gerçek kodu satır numaralarıyla yer alır.

BileşenGörevi
AdminControllerEkranı açar, formu alır, doğrular ve kaydeder.
ContentPageİçerik entity’si; bu projede aynı zamanda edit formunun modeli.
LoginModelYalnızca giriş formunun veri modeli.
Edit.cshtmlEntity alanlarından input üretir.
editor.jsGörsel metin alanlarını BodyHtml değerine aktarır.
SitePageViewModelZiyaretçi ekranı için entity ve listeleri paketler.
Her bölümde üç soruyu sorun: Bu veri nereden geliyor? Şimdi bellekte mi, veritabanında mı? Sonuç hangi view’da kullanılıyor?
DERS 02 · BÖLÜM 02

Sınıf, bağımlılıklar ve yetki

Constructor’da neden hem db hem configuration var?

[Authorize(Policy = "AdminAccess"), Route("admin")]
public class AdminController(
    SiteDbContext db, IConfiguration configuration) : Controller

db veritabanına erişir. configuration JSON ve ortam değişkenleri gibi kaynaklardan ayar okur. İkisi de ASP.NET Core tarafından constructor’a verilir; controller bağlantı veya ayar dosyasını kendi açmaz. Bu bağımlılıkların kayıt/yükleme düzeni Program.cs’de kurulmuştur.

Route("admin") ortak adres önekidir. Bir action’daki HttpGet("posts/new") ile birleşince GET /admin/posts/new olur. Authorize, AdminAccess politikasını ister. Politikanın ayrıntısı Program.cs’de tanımlıdır: giriş kontrolü kapalıysa izin ver, açıksa kimliği doğrulanmış kullanıcı iste.

Ayar / nitelikSonuç
Admin:RequireAuthentication=falseŞu anki durum: /admin giriş istemez; düzenleme de anonim yapılabilir.
Admin:RequireAuthentication=trueOturumsuz kullanıcı admin ekranı için login’e yönlendirilir.
AllowAnonymousLogin action’larına oturum açmadan erişilebilmesini sağlar.
EnableRateLimiting("login")Login POST için tanımlı IP bazlı hız sınırını uygular.

Authentication “kimlik var mı?”, authorization “bu endpoint için izin var mı?” sorusudur. AllowAnonymous bu sayfadaki form doğrulamasını veya CSRF korumasını kapatmaz. Giriş açık/kapalı tercihi ile formun güvenli gönderilmesi ayrı konulardır.

Şu an login ekranı görünmüyor diye giriş kodu silinmiş değil. Ayar false olduğu için Login action’ı /admin’e yönlendiriyor.

DERS 02 · BÖLÜM 04

Index: listeyi ekrana taşıma

Veritabanı sıralaması ile view içindeki gruplama arasındaki fark.

public async Task<IActionResult> Index() =>
    View(await db.Pages.AsNoTracking()
        .OrderBy(p => p.IsDetail)
        .ThenBy(p => p.Title)
        .ToListAsync());

AsNoTracking okuma içindir. OrderBy önce sabit sayfaları, ardından detayları sıralar; ThenBy aynı grup içinde başlığa göre sıralar. ToListAsync sonuçları getirir. View adı verilmediği için action adı Index kullanılır; dosya Views/Admin/Index.cshtml olur.

@model List<ContentPage>
@foreach (var detail in new[] { false, true })
{
    foreach (var entry in Model.Where(p => p.IsDetail == detail))
    {
        <a href="@entry.Url">@entry.Title</a>
    }
}

Bu Razor örneği sadeleştirilmiştir. Önemli fark: Controller’daki LINQ EF sorgusudur; view’daki Model artık bellekte List<ContentPage> olduğundan Where bellekte gruplar. View’daki her Where yeni SQL göndermez.

Admin listesi Published filtresi kullanmaz. Taslaklar da görünmelidir; aksi halde onları yeniden yayınlamak veya düzeltmek mümkün olmazdı. Ziyaretçi listesi ise yalnızca yayınlanmış kayıtları gösterir.

Düzenleme bağlantısı IsDetail değerinden üretilir: sabit sayfada /admin/pages/about/edit, yazıda /admin/posts/ilk-yazim/edit. Url ise ziyaretçi bağlantısıdır. Yönetim linki ile ziyaretçi linkinin aynı olmaması gerekir.

View model alanı ile HTML etiketi aynı şey değildir: Title veridir; onu h1, td veya a içinde göstermek view’ın kararıdır. Görünümü değiştirmek her zaman veritabanı değişikliği gerektirmez.
DERS 02 · BÖLÜM 05

Editor: mevcut formu açma

GET sırasında BodyHtml değişiyor; bu hemen veritabanına yazılır mı?

var page = await db.Pages.AsNoTracking()
    .SingleOrDefaultAsync(p => p.Slug == slug && p.IsDetail == detail);
if (page == null) return NotFound();
page.BodyHtml = page.IsDetail ? BlogMarkup.ArticleBody(page.BodyHtml)
    : page.Slug is "home" or "blog"
        ? BlogMarkup.ListingTemplate(page.BodyHtml) : page.BodyHtml;
return View("Edit", page);
  1. URL’deki slug ve route’un belirlediği detail ile kayıt aranır.
  2. Kayıt yoksa NotFound ile işlem sonlanır.
  3. Blog detayında eski şablondan yalnızca makale gövdesi çıkarılır.
  4. Ana sayfa/blogda örnek kart alanı BLOG_LIST işaretine uyarlanır.
  5. Hazırlanan ContentPage, Edit.cshtml’e gönderilir.

Burada page.BodyHtml ataması yalnızca bellekteki nesneyi değiştirir. Sorgu AsNoTracking ile çalışmıştır ve SaveChangesAsync de çağrılmamıştır. Formu açıp kapatmak veritabanını güncellemez. Ancak bu hazırlanmış değer formda görünür; kullanıcı kaydederse POST yolundan kalıcı olur.

Neden Published kontrolü yok? Taslak yazının editörü de açılmalıdır. Neden ArticleBody uygulanıyor? Yönetici makale yazarken header/footer ve eski örnek yorumlarla uğraşmasın; dinamik başlıklar ayrı alanlardan yönetilsin.

Bir nesnenin özelliğine değer atamak her zaman SQL UPDATE değildir. Kalıcılık için doğru context takibi ve kaydetme adımı gerekir. Bu ayrım GET ile POST arasındaki en önemli farklardan biridir.

New: kayıt oluşturmadan form hazırlamak

Yeni nesne ile yeni veritabanı satırı aynı şey değildir.

public IActionResult New() => View("Edit", new ContentPage {
    IsDetail = true, Published = false, Category = "Genel",
    CoverImageUrl = "/images/blog-post-bg.jpg",
    BodyHtml = "<section><p>Yazınızı buraya ekleyin.</p></section>"
});

HTML örneği kısaltılmıştır. new ContentPage bellekte bir nesne oluşturur. Add ve SaveChanges olmadığı için tabloya satır eklenmez. Id varsayılan int değeri 0 olduğu için Edit view’ı “Yeni detay” başlığını seçer; mevcut kayıtta ise Title gösterir.

Başlangıç alanıNeden böyle?
IsDetail=trueBu ekran blog yazısı oluşturuyor.
Published=falseTamamlanmamış yazı kaydedilirse hemen ziyaretçiye açılmasın.
Category="Genel"İlk form için düzenlenebilir başlangıç değeri.
CoverImageUrlBaşlangıç görsel yolu; dosya yüklemez.
BodyHtmlGörsel editörün düzenleyebileceği başlangıç paragrafı.

Neden ayrı New.cshtml yok? Yeni yazı ve mevcut yazı aynı alanları düzenliyor. Tek Edit view’ı ile alan görünümü ve hata gösterimi ortak tutuluyor. Formun gönderildiği URL farklı olduğu için POST yeni kayıtta Create action’ına, mevcut kayıtta SavePost action’ına gidiyor.

ContentPage sınıfında Published varsayılanı true olmasına rağmen New burada açıkça false veriyor. Nesne oluşturulurken yapılan bu atama başlangıç değerini değiştirir. Böylece aynı model farklı kullanımda farklı başlangıç davranışı gösterebilir.

Tarayıcıda formu açmak, sayfayı yenilemek veya vazgeçmek bir yazı oluşturmamalıdır. Yeni kayıt ancak başarılı POST akışındaki Add + SaveChangesAsync ile oluşur.

Edit.cshtml: input nereden değer alıyor?

asp-for, name ve model binding ilişkisi.

@model ContentPage
<form method="post">
    @Html.AntiForgeryToken()
    <div asp-validation-summary="All"></div>
    <label asp-for="Title">Başlık</label>
    <input asp-for="Title" maxlength="160" required>
    <textarea asp-for="Description"></textarea>
    <input asp-for="Published">
    <textarea asp-for="BodyHtml"></textarea>
    <button>Değişiklikleri kaydet</button>
</form>

Bu, mevcut formun sadeleştirilmiş halidir. @model ContentPage view’ın beklediği türü belirtir. Model, controller’dan gelen nesnedir. asp-for="Title" modeldeki Title özelliğine bağlanır; name="Title", id ve mevcut değer gibi HTML özelliklerini üretir. Model binding POST’taki Title değerini input.Title özelliğine taşır.

Formda action yok; tarayıcı POST’u mevcut URL’ye gönderir. Label’daki asp-for etiketi ilgili inputla ilişkilendirir. HTML placeholder örnek ipucudur, veritabanına kaydedilecek gerçek değer değildir.

View’daki ifadeGönderim / anlam
input asp-for="Title"Title adlı form alanı → input.Title
textarea asp-for="BodyHtml"HTML metni → input.BodyHtml
input asp-for="Published"Bool checkbox; false gönderimi için yardımcı hidden alan da üretilebilir.
Html.AntiForgeryToken()CSRF kontrolüne ait gizli token; entity alanı değil.
asp-validation-summary="All"ModelState içindeki hataları kullanıcıya gösterir.
Sadece name="BaskaAd" yaparsanız Title ile otomatik eşleşme bozulur. Etiket metnini “Yazı başlığı” yapmak ise binding’i değiştirmez. Kullanıcının gördüğü label ile sunucunun bağladığı alan adı ayrı şeylerdir.

Koşullu alanlar ve layout

Neden bazı inputlar yalnızca blogda görünüyor?

Edit view’ında Model.IsDetail kontrolü kapak, kategori, yazar ve yazı tarihini yalnızca blog detayında gösterir. Sabit sayfada Slug readonly olur. Ana sayfa ve blog sabit sayfasında ise kartların otomatik oluştuğunu anlatan bilgi gösterilir.

@if (Model.IsDetail)
{
    <input asp-for="Author">
    <input asp-for="PublishedAtUtc" type="datetime-local"
           asp-format="{0:yyyy-MM-ddTHH:mm}">
}

Tarih formatı inputun beklediği biçimi sağlar. datetime-local saat dilimi taşımaz; projede alan açıkça UTC diye etiketlenmiştir. Controller’da SpecifyKind(...Utc) sayısal saati dönüştürmez, UTC olarak işaretler. Yerel saati otomatik UTC’ye çevirdiğini düşünmeyin.

  1. Views/_ViewImports.cshtml modellerin namespace’ini ve MVC Tag Helper’larını etkinleştirir.
  2. Kök _ViewStart normal _Layout seçer; Admin/_ViewStart bunu _AdminLayout ile değiştirir.
  3. _AdminLayout header, admin.css, çıkış formu ve bildirim alanını içerir.
  4. RenderBody(), Index/Edit/Login view’ının HTML’sini ortak kabuğa yerleştirir.

Admin view’ları kendi başlarına tam html/head/body belgeleri değildir. Ortak kabuk layouttan gelir. Ziyaretçi Page.cshtml ise Layout=null kullanır ve tam belgeyi kendisi kurar. Aynı yaklaşımı her ekrana zorla uygulamak yerine mevcut yapının amacını görmek önemlidir.

Readonly görünüm için yararlıdır ama sunucu güvenliği değildir. Kullanıcı farklı POST gönderebilir. Save metodunda sabit slug’ın değişmediği ayrıca kontrol edilir.
DERS 02 · BÖLÜM 09

POST: route değeri mi, form değeri mi?

Slug değiştirirken iki farklı slug aynı anda vardır.

public Task<IActionResult> SavePost(
    [FromRoute] string slug, ContentPage input)
    => Save(slug, true, input);

public Task<IActionResult> Create(ContentPage input)
    => Save(null, true, input);

Örnek: URL /admin/posts/eski-ad/edit, formdaki Slug ise yeni-ad. slug parametresi mevcut kaydı bulmak için eski-ad olmalıdır. input.Slug yeni kaydedilecek değerdir. FromRoute özellikle URL’deki değerin kullanılacağını belirtir; formdaki aynı isimli alanla karışmasını engeller.

DeğerKaynağıAmacı
oldSlugURL; yenide nullMevcut kaydı bulmak / yeni kayıt ayrımı
input.SlugPOST formuKaydedilecek yeni adres
detailSavePost/SavePage action’ıYazı mı sabit sayfa mı?
inputModel bindingGönderilen alanları taşıyan geçici nesne

SavePage false, SavePost true, Create null/true gönderir. Kullanıcının formda IsDetail=true göndermesi sabit sayfa endpointini blog endpointine dönüştürmez; Save bu değeri route’a göre yeniden atar.

Task doğrudan döndürüldüğünden bu kısa action’larda async/await yoktur. Asenkron işlemler ortak Save içinde beklenir. Metotların küçük olması işin önemsiz olduğunu değil, işi tek ortak yere aktardığını gösterir.

Bu action’lar yalnızca POST kabul eder. Aynı URL’ye GET ile gitmek düzenleme formunu açan action’ı seçer; kayıt işlemini çalıştırmaz.
DERS 02 · BÖLÜM 10

Save: input ve page neden iki nesne?

İstemci verisini gerçek entity’ye kontrollü aktarmak.

input.IsDetail = detail;
var page = oldSlug == null
    ? new ContentPage { IsDetail = true }
    : await db.Pages.SingleOrDefaultAsync(p =>
        p.Slug == oldSlug && p.IsDetail == detail);
if (page == null) return NotFound();
input.Id = page.Id;

input, formdan gelen nesnedir. page, veritabanından yüklenen takipli kayıt veya yeni oluşturulan gerçek entity’dir. Burada AsNoTracking kullanılmaz; mevcut page üzerindeki değişikliklerin SaveChangesAsync tarafından bulunması istenir.

oldSlug null ise yeni kayıt oluşturulur. Null değilse doğru tür ve eski slug ile kayıt aranır. Başkası kaydı kaldırmışsa veya URL yanlışsa NotFound döner. input.Id gerçek page.Id ile değiştirilir; gelen Id değerine güvenilmez. Bu Id özellikle hata halinde edit view’ının mevcut/yeni kayıt ayrımı için de önemlidir.

page.Title = input.Title;
page.Slug = input.Slug;
page.Description = input.Description ?? "";

Neden doğrudan db.Update(input) kullanılmıyor? İstemci tarafından gönderilebilecek tüm entity özelliklerinin otomatik kayda aktarılması yerine hangi alanların değişeceği açıkça seçiliyor. IsDetail, Id ve UpdatedUtc sunucunun kontrolünde tutuluyor. Bu yaklaşım ayrı input modeli bulunmasa bile kontrolü artırıyor.

Bu işlem yeni HTTP isteğinde gerçekleşir. GET’te oluşturulan page nesnesi POST boyunca bellekte bekletilmiyor. POST kendi inputunu oluşturuyor ve gerçek kaydı yeniden veritabanından yüklüyor.
DERS 02 · BÖLÜM 11

Doğrulama: neden üç katman var?

HTML, ModelState ve veritabanı birbirinin yerine geçmez.

if (!detail && oldSlug != input.Slug)
    ModelState.AddModelError("Slug", "Sabit sayfaların route’u değiştirilemez.");
if (await db.Pages.AnyAsync(p => p.IsDetail == detail
    && p.Slug == input.Slug && p.Id != page.Id))
    ModelState.AddModelError("Slug", "Bu slug zaten kullanılıyor.");
if (!ModelState.IsValid) return View("Edit", input);

AnyAsync yalnızca böyle bir kayıt var mı diye sorar; liste getirmez. p.Id != page.Id koşulu, mevcut yazının kendi slug’ıyla çakışmış sayılmamasını sağlar. Başka kayıtta aynı tür/slug varsa hata eklenir.

KatmanÖrnekNeden var?
Tarayıcırequired, maxlength, readonlyHızlı kullanıcı geri bildirimi; tek güvence değil.
Model / controllerRequired, regex, ModelStateTarayıcı dışından gelen isteği de denetler.
VeritabanıUNIQUE(IsDetail,Slug)Eşzamanlı iki isteğin aynı slug’ı oluşturmasına son engel.

ModelState model binding sırasında oluşan dönüştürme hatalarını ve doğrulama hatalarını tutar. Örneğin tarih alanı tarihe çevrilemiyorsa veya slug büyük harf içeriyorsa geçersiz olabilir. Hata halinde View("Edit", input) kullanıcının girdilerini koruyarak aynı formu gösterir; redirect yapılmaz.

AddModelError("Slug", ...) belirli alana; AddModelError("", ...) genel forma hata ekler. asp-validation-summary="All" ikisini de gösterebilir. ModelState’in sakladığı gönderilmiş değerler, hata formunda Tag Helper’ların yeniden çizdiği değerlere öncelik verebilir; model özelliğini değiştirmek her zaman ekrandaki hatalı girdiyi değiştirmez.

HTTP 200, kaydın başarılı olduğunu tek başına göstermez. Geçersiz form da hata mesajlarıyla 200 dönebilir. Başarılı Save akışı burada redirect üretir.
DERS 02 · BÖLÜM 12

Alan atamaları ve boş değerler

Null, boş string ve tarih kararlarının amacı.

page.CoverImageUrl = string.IsNullOrWhiteSpace(input.CoverImageUrl)
    ? null : input.CoverImageUrl.Trim();
page.Category = string.IsNullOrWhiteSpace(input.Category)
    ? null : input.Category.Trim();
page.Author = string.IsNullOrWhiteSpace(input.Author)
    ? null : input.Author.Trim();
page.PublishedAtUtc = DateTime.SpecifyKind(input.PublishedAtUtc, DateTimeKind.Utc);

Bu alanlar yalnızca detail=true için atanır. IsNullOrWhiteSpace null, boş metin veya sadece boşluk girilmiş olmasını tek yerde kontrol eder. Dolu değerler Trim ile baş/son boşluklarından temizlenir. Böylece " Gezi " gibi istemeden farklı görünen değerler azaltılır.

Description farklı davranır: input.Description ?? "". DbContext bu sütunu zorunlu tanımladığı için null yerine boş string saklanır. Modelin C# tarafında nullable olması ile veritabanının null kabul etmesi ayrı ayarlardır.

BodyHtml için blogda ArticleBody, ana sayfa/blog listesinde ListingTemplate uygulanır. Bu, bilinen Voku şablon yapısını düzenler; genel bir HTML sanitizer değildir. Published formdan alınır, UpdatedUtc ise DateTime.UtcNow ile sunucuda yenilenir.

TarihAmacı
PublishedAtUtcYönetilebilir gösterim ve sıralama tarihi. İleri tarih otomatik zamanlama oluşturmaz.
UpdatedUtcSon kaydın sunucu zamanı. Kullanıcı formundan alınmaz.
Görsel alanının regex’i adres biçimini sınırlar; dosyanın gerçekten var olduğunu veya yüklenebildiğini kanıtlamaz. Kapak yolu yazmak bir dosya upload işlemi değildir.
DERS 02 · BÖLÜM 13

INSERT, UPDATE ve slug bağlantıları

Add ile SaveChangesAsync neden ayrı?

LoginModel, hash ve cookie

Giriş kontrolü tekrar açılırsa bu kod nasıl çalışacak?

  1. GET Login(), ayar true ise new LoginModel ile Login.cshtml açar; false ise Index’e yönlendirir.
  2. POST Login(input), önce ayarı ve ModelState’i kontrol eder.
  3. AdminUsers içinde Username eşleşen kullanıcıyı arar.
  4. Kayıt yoksa veya PasswordHasher doğrulaması başarısızsa genel hata mesajı verir.
  5. Başarıda kullanıcı adı claim’i olan kimlik oluşturur; SignInAsync authentication cookie’sini üretir.
  6. Index’e yönlendirir. Sonraki isteklerde middleware cookie’den kullanıcı kimliğini okur.
  7. POST Logout(), SignOutAsync ile tarayıcı oturumunu kapatır; login’e yönlendirir.

LoginModel.Password düz şifre girişidir; AdminUser.PasswordHash saklanan doğrulama değeridir. Şifreyi bulmak için hash’i geri çözme akışı yoktur. DataType.Password inputun görünümünü belirtir; kendisi hashleme yapmaz. Hash kontrolünü PasswordHasher yapar.

ClaimsPrincipal kullanıcının kimlik bilgisini taşır. ClaimTypes.Name bu kodda kullanıcı adıdır. Tam ASP.NET Core Identity kullanıcı/rol sistemi kurulmuş değildir; yalnızca PasswordHasher ve cookie authentication bileşenleri kullanılır. Rol tabanlı yetki ayrımı yoktur.

Cookie adının Voku.Admin olması ve dört saatlik bilet süresi Program.cs’de ayarlanır. Login POST için IP bazlı dakikada 10 istek limiti tanımlanır. Çıkışın POST olması, durum değiştiren bir işlem olmasıyla uyumludur; layout formu antiforgery token gönderir.

Şu an ayar false olduğu için hesap şifresi bu ekranların ön koşulu değil. Buna rağmen login akışını öğrenmek, ayar yeniden true yapıldığında hangi kodun devreye gireceğini anlamanızı sağlar.

  1. GET Editor, BodyHtml’yi Edit view’ına gönderir.
  2. asp-for textarea’sı bu değeri taşır.
  3. JavaScript görsel alanları oluşturur.
  4. Kullanıcı paragrafı değiştirir; sync() tüm body HTML’sini textarea’ya yazar.
  5. Normal form POST’u BodyHtml alanını gönderir.
  6. Save input.BodyHtml değerini gerçek entity’ye aktarır ve kaydeder.

Bir düzenlemeyi baştan sona izleyelim

Yazar adını değiştirip ziyaretçi kartında görelim.

  1. GET /admin/posts/ilk-yazim/edit → EditPost → Editor.
  2. Editor ContentPage’yi alır; Edit view’ında input asp-for="Author" mevcut yazar adıyla dolar.
  3. Kullanıcı Author alanına “Ayşe” yazar. Henüz SQLite değişmez.
  4. Form POST olur; token doğrulanır, model binding input.Author="Ayşe" yapar.
  5. SavePost eski slug’ı route’tan alır ve Save’e aktarır.
  6. Save gerçek page entity’sini takipli yükler, doğrulamayı kontrol eder.
  7. Trim edilmiş Author değeri page.Author’a atanır; UpdatedUtc güncellenir.
  8. SaveChangesAsync veritabanını yazar. TempData mesajı konur, edit URL’sine yönlendirilir.
  9. Yeni GET formda “Ayşe”yi gösterir.
  10. Ziyaretçi /blog açınca SiteController Posts listesinde güncel entity’yi getirir; _BlogListing @post.Author ile “Ayşe”yi gösterir.

Hata varyasyonu: Aynı anda geçersiz slug gönderin. ModelState başarısız olduğundan SaveChanges’e ulaşılmaz. Formda girdiğiniz yazar adı görünebilir ama veritabanındaki yazar değişmemiş olabilir. Formda bir değerin görünmesi tek başına kaydedildiğinin kanıtı değildir.

Taslak varyasyonu: Published kutusunu kaldırıp kaydedin. Admin listesi kaydı göstermeye devam eder; ziyaretçi listesi ve detay sorgusu Published şartıyla dışlar. Veritabanından silinmemiştir, yayın durumu değişmiştir.

Breakpoint noktaları: Save başlangıcı → ModelState kontrolü → page.Author ataması → SaveChangesAsync sonrası. input ile page değerlerini ayrı ayrı izleyin. Tarayıcı Network’te POST ve takip eden GET’i görün.
